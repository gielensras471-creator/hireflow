## 0. 首次使用说明：如何让这份总纲发挥作用

1. 将本文上传至 **HireFlow ChatGPT 项目的「来源 / 文件」**，文件名建议保持稳定。
2. 在同一 ChatGPT 项目内保留三个对话：
   - **A｜01 · V3.0 项目总控与进度管理**（当前用于管理的对话）
   - **B｜02 · V3.0 产品研究与需求分析**（竞品 / 需求 / PRD）
   - **C｜03 · V3.0 UI/UX 设计研究**（视觉参考 / 信息架构 / Figma）
3. 每次进入任一对话时，先说：**“请以项目来源中的《HireFlow V3.0 项目主控总纲》为调度依据，核对当前进度；本对话只处理分配给它的工作。”**
4. 每完成一个节点，按照本文 **第 7 节交接格式**产出简短摘要，回到 **A 对话**做验收与进度更新，再跳转到下一指定对话。
5. **重要**：三个对话不会因这份文件而自动实时同步各自的所有消息。项目来源中的总纲只有在**用户上传更新后的版本**时才会更新；尚未同步的阶段结果须通过摘要或文件带过去。

### 文件优先级（遇到内容不一致时）

- **最新经用户确认的决策** > **已批准的 PRD / UI 设计规范** > **最新主控总纲的进度状态** > **旧《HireFlow V3.0 实施总纲》** > **早期聊天讨论与未经核实的建议**。
- **事实证据**另看源码、Codex 审计报告和测试结果；总纲中的“计划实施”不等于“已经实现”。
- 原始《HireFlow V3.0 实施总纲》保留作为项目背景和技术边界文件；**本文作为多对话调度与进度管理的唯一主控入口**。

## 1. 项目背景、已冻结的方向与不做事项

### 1.1 项目定位

- **项目名称**：HireFlow。
- **开发基线**：V2.1.1，固定审计提交 `490b9ee2f1985b37052feebefd73605aa0dba1ab`。
- **远程仓库**：<https://github.com/gielensras471-creator/hireflow>。
- **V3.0 方向**：**方案 A——保留企业招聘流程协作平台定位**；主要面向小型企业或小规模招聘团队。**不转型为个人投递工具 JobTrack**，不从零推翻重做。
- **求职目标**：将项目打磨成可信、可运行、可展示、可解释的前端实习作品，展现业务分析、Vue3/TS、UI/UX、前后端联动和工程能力。
- **原则**：不追求表面“藏 AI 痕迹”，而是让业务规则、数据、交互与技术实现有明确依据。

### 1.2 保留技术栈

- 前端：Vue 3、TypeScript、Pinia、Vue Router、Axios、Element Plus、ECharts、Vite、Sass。
- 后端：Node.js、Express、JWT、bcryptjs、SQLite（`node:sqlite`）。
- 已有生产部署**按项目文档声称**为 Render 前端 + 腾讯云 Lighthouse / Nginx / PM2 / HTTPS 后端；尚未因第一批审计验证其实时运行状态。
- 无业务需要，不更换 MongoDB、不引入复杂微服务、不过度堆框架。

### 1.3 V3.0 已冻结的产品重点（以 PRD v1.0 为准）

1. **面试结束、面试评价与招聘决策分离**，取消“面试完成就自动推进 / 复面完成即 Offer”的行为。
2. **后端统一约束招聘阶段和操作资格**，避免仅靠前端按钮限制。
3. **真实活动历史**：记录操作时间、动作、操作者及必要备注；详情页不得以当前阶段伪造完整事件链。
4. **职位关系和统计口径一致**：采用稳定标识关联，定义职位候选人数量的计算规则。
5. **任务型工作台**：优先呈现待筛选、待面试、待评价、待决策及可执行入口。
6. **简洁、专业、可辨识的 B 端体验**：调整文案、信息密度、状态、空态及关键页面交互。
7. **可验证**：补关键流程自动化测试，准备逻辑自洽的演示数据。

### 1.4 V3.0 当前明确不做（详见已冻结 PRD §3.3）

AI 简历解析 / RAG / Agent、第三方招聘渠道 / 邮件 / 日历集成、复杂 RBAC 和多租户、微服务、无使用场景的虚拟滚动、数据库无理由迁移、编造的效率或性能数字。后续如确有证据再另立版本。
