## 一、验收原则与通用前置条件

### 1.1 执行前必须具备

- [ ] 已由 01 总控批准 PRD 与产品边界，明确当前待验收的 Git 提交/分支。
- [ ] 测试在隔离的本地或测试环境中执行；**不能用生产数据库验证或重置**。
- [ ] 准备虚构的职位、候选人申请、面试和 Offer 数据，并记录测试数据 ID。
- [ ] 使用至少一个真实可登录的 HR / 招聘管理员账号；能够检查服务端真实操作者和时间。
- [ ] 可检查前端展示、后端接口响应与 SQLite 的实际最终状态/事件记录。
- [ ] 对迁移场景准备旧版数据库的**副本**和回滚验证环境，保留迁移前后核对结果。
- [ ] 测试业务时区固定为 `Asia/Shanghai`；“今日”为该时区 `[00:00, 次日00:00)`；预约到时提醒按开始时刻 `scheduled_at <= now`（不假定存在结束时间）。

### 1.2 证据格式

每项测试记录 **环境/版本、数据 ID、操作步骤、实际结果、预期结果、截图或接口/数据库证据、执行人、日期、结论**。可使用下表记录结果：

| 结果状态 | 含义 |
|---|---|
| 未执行 | 目前全部用此状态；没有运行证据 |
| 通过 | 已执行，前端/接口/数据与预期一致，有可核查证据 |
| 失败 | 实测与预期不一致，记录复现步骤和问题编号 |
| 阻塞 | 缺少可用测试前置条件或被其他缺陷阻止 |
| 不适用 | 仅经总控认可该场景与当前实施范围不符时使用，不能随意跳过 P0 |

**优先级标记**：S = 阻断性规则/数据缺陷；M = 必须在验收前解决的关键体验或统计问题。以下表中的等级是测试优先度，不是开发优先级。

## 二、P0 核心验收项（AC-01～AC-36；保留原 AC-01～AC-32 编号）

> 每条都是“前置 → 操作 → 可检查结果”。以下全部**未执行**，勾选状态待后续开发/测试阶段填写。方法中的 UI/API/DB 表示至少要关注的证据，不强制绑定具体接口 URL 或表名。

### A. 职位与申请关系（P0-01）

- [ ] **AC-01｜新增申请稳定关联职位**（S）  
  前置：J01 为开放职位。操作：HR 在真实职位列表选择 J01，新增 R01。  
  预期：持久化申请关联 J01 的稳定 ID；列表/详情职位名称一致；J01 申请数按关联记录增加，其他职位不变。**证据：UI + API + DB**。

- [ ] **AC-02｜同名职位不互相污染**（S）  
  前置：J01、J02 同名不同 ID。操作：分别新增申请并修改/关闭其中一个职位。  
  预期：每条申请归属明确；各自统计独立，未选定的职位和申请不受影响。**证据：API + DB + UI**。

- [ ] **AC-03｜职位更名关系不丢失**（S）  
  前置：J01 已有 R01 和面试。操作：将 J01 名称更新。  
  预期：申请外键、面试关系不变；展示新名称时来源明确；历史不被伪造成曾经使用新名称；计数不变化。**证据：UI + DB**。

- [ ] **AC-18｜申请数不是去重自然人数**（M）  
  前置：同一虚构人员张三分别申请 J01、J03。操作：查看申请列表、职位统计及 Dashboard。  
  预期：两条独立申请，进度和事件互不污染；指标用“申请记录数”，不宣称系统计算了去重自然人数。**证据：UI + DB**。

- [ ] **AC-19｜关闭/删除职位的关联保护**（S）  
  前置：J01 存在活跃申请。操作：尝试关闭职位、随后删除职位；另准备一个已关闭职位尝试新增申请。  
  预期：关闭不自动淘汰现有申请，明确提醒；有关联时不能无提示硬删；新申请不能默认关联关闭职位。**证据：UI + API + DB**。

### B. 招聘阶段、决策和结果（P0-02 / P0-03）

- [ ] **AC-04｜面试完成不自动晋级**（S）  
  前置：R01 位于初面，存在 scheduled 初面。操作：HR 将面试标记 completed。  
  预期：面试变 completed；R01 仍在 first_interview，active；无虚假的晋级历史。**证据：UI + API + DB**。

- [ ] **AC-05｜推荐通过不等于 HR 决策**（S）  
  前置：AC-04 完成。操作：提交 `recommend` 评价。  
  预期：面评保存并可查看，但 stage 仍未变；不生成“HR 批准”事件。**证据：UI + DB**。

- [ ] **AC-06｜HR 明确晋级与真实事件**（S）  
  前置：R01 在初面，面试已完成且评价齐备，无 scheduled 面试。操作：HR 确认进入复面。  
  预期：stage 由 first_interview→second_interview，新增唯一真实事件，含 HR01、服务端时间和原/新阶段。**证据：UI + DB**。

- [ ] **AC-08｜绕过 UI 的非法阶段变更被后端拒绝**（S）  
  前置：R01 在初面。操作：直接对接口请求变更为 Offer、rejected 阶段或任意不在合法表中的值。  
  预期：后端返回明确错误（如 400/409），实际阶段与历史均不变；不只是前端按钮隐藏。**证据：API + DB**。

- [ ] **AC-10｜企业在初面终止（合法组合）**（S）
  前置：R01 `active/first_interview`，无 `scheduled`。操作：HR 选企业淘汰，输入原因。
  预期：`closed/first_interview/company_rejected`、`offer_status=null`，保留阶段及结束原因/时间/操作者；不伪造面试失败结论。**证据：UI + API + DB**。

- [ ] **AC-11｜候选人在复面退出（合法组合）**（S）
  前置：R03 `active/second_interview`，无 `scheduled`。操作：HR 记录候选人主动退出及原因。
  预期：`closed/second_interview/candidate_withdrew`、`offer_status=null`，不计入企业淘汰；直接把 outcome 改为 `offer_declined` 应由后端拒绝。**证据：UI + API + DB**。

- [ ] **AC-20｜已结束申请只允许面评有痕纠错例外**（S）
  前置：R01 `closed`，有一条原本已提交的面评与另一场无评价的已完成面试。操作：尝试推进、再次结束、新排面试、Offer 变更或对缺评面试新建评价；另外对原面评执行合法“更正”操作。
  预期：普通招聘操作及新增缺评被后端拒绝，无非法事件；唯一允许的面评更正遵守 AC-34，有痕且不改变 `stage/application_status/outcome`。**证据：UI + API + DB**。

### C. 柔性校验、幂等与事务（P0-03 / P0-06 / P0-08）

- [ ] **AC-07｜缺评理由晋级并留存豁免事实**（S）
  前置：R01 初面已 `completed` 但缺 Feedback、无 `scheduled`。操作：尝试晋级（先不填理由，后填写理由）。
  预期：明确列出缺评面试 ID；空理由拒绝；有理由才推进；事件保留原阶段、缺评清单、原因、操作人和时间；不会产生虚构评价。历史缺评标注“已说明原因推进”，不再计入**新阶段**的当前待面评。**证据：UI + API + DB/聚合**。

- [ ] **AC-14｜重复/并发晋级不会连跳或生成双事件**（S）  
  前置：R01 初面满足推进条件。操作：快速点击或并发重复提交相同推进请求。  
  预期：最多发生一次初面→复面；不得在重试中变 Offer，不新增重复事件；冲突或重复响应行为可解释。**证据：API + DB**。

- [ ] **AC-15｜业务变更与事件原子性**（S）  
  前置：隔离测试环境可以模拟事件写入失败。操作：使“推进阶段”或“结束申请”的业务数据更新成功条件满足，但其事件写入失败。  
  预期：事务整体回滚；阶段/结果与历史均无部分成功。**证据：故障注入 + DB**。

- [ ] **AC-25｜跳过评估理由与未处理预约拦截**（S）
  前置：两条初面申请无 `completed`。操作：第一条未填原因尝试推进，后填“跳过本轮面试评估”理由推进；第二条先安排 `scheduled` 后尝试推进。
  预期：无已完成面试时必须有非空跳评估原因；存在有效预约不能绕过，先完成/取消；例外事件记录事实，不创建虚拟面试或面评。**证据：UI + API + DB**。

### D. 面试管理与面评（P0-04 / P0-05）

- [ ] **AC-09｜面试改期、取消不改变阶段**（S）  
  前置：R01 初面 scheduled。操作：改期并保存，再取消并填写原因。  
  预期：stage 不变；新旧日期和取消理由有真实事件；取消不是淘汰。**证据：UI + DB**。

- [ ] **AC-21｜预约开始时间已到，面试仍待人工确认**（M）
  前置：时区 `Asia/Shanghai`，某面试 `scheduled`，预约开始时间刚好等于固定的当前时刻；另有一场未来预约。操作：刷新面试列表/详情与 Dashboard。
  预期：刚到预约开始时间的面试显示“预约开始时间已到，待确认面试状态”，仍 `scheduled`；未来预约没有该提示；无 `completed_at` 或完成事件。**不使用不存在的预约结束时间**。**证据：UI + DB + 固定时间测试**。

- [ ] **AC-22｜同阶段允许顺序多场，限制并行预约**（S）  
  前置：R01 初面已有 scheduled 面试。操作：再创建一场 scheduled；取消第一场后再创建；第二场完成后创建补充面试。  
  预期：存在预约时拒绝第二场并行预约；前一场已取消/完成后允许同阶段新建；每场有独立 ID、时间、状态和待办；不会自动改 stage。**证据：API + DB + UI**。

- [ ] **AC-23｜面评前提、唯一有效记录与普通覆盖禁止**（S）
  前置：一场 `scheduled` 和一场 `completed` 的活跃申请面试。操作：对两者分别提交评价，并对已提交的评价尝试普通重复 POST/PATCH。
  预期：仅 `completed` 能首次提交，专业评价人、推荐、非空理由齐全；同场至多一份当前有效面评；普通再次提交/无更正理由覆盖被拒。**正式误录更正采用 AC-34，不计第二份有效评价**。**证据：API + DB**。

- [ ] **AC-24｜面试官姓名与实际 HR 录入账号独立**（S）
  前置：HR01 登录，为专业面试官“李某”代录评价。操作：首次提交，查看面评/事件；再按规则有痕更正评价人或结论。
  预期：首次评价的专业来源显示“李某”，实际录入为 HR01；更正事件记录当次真实账号与旧/新值，无任何“李某本人登录”伪造事实。**证据：UI + DB**。

### E. Offer 与结束结果（P0-07）

- [ ] **AC-12｜Offer 拒绝原子关闭且不可跨阶段使用**（S）
  前置：申请为 `active/offer/sent`；另准备 `active/offer/preparing` 和 `active/second_interview` 记录。操作：第一条登记候选人拒绝并填写原因，另两条直接请求 `offer_declined`。
  预期：第一条同一事务成为 `closed/offer/declined/offer_declined`，事件与原因完整，不计 `hired`；另两条被后端拒绝且状态/事件不变。**证据：UI + API + DB/统计**。

- [ ] **AC-13｜Offer 接受后由 HR 确认录用**（S）
  前置：申请 `active/offer/sent`。操作：登记 `accepted`，观察申请后再执行“确认录用”；另尝试在 `sent` 直接录用。
  预期：接受后仍为 `active/offer/accepted/outcome=null`，确认后才 `closed/offer/accepted/hired`；直接 `sent→hired` 被拒；两次合法动作各有真实事件。**证据：UI + API + DB**。

- [ ] **AC-26｜进入 Offer 仅代表 preparing**（S）
  前置：R01 从复面合法进入 Offer。操作：查看 Offer、当前申请及 Dashboard，再尝试直接“确认录用”。
  预期：`active/offer/preparing/outcome=null`；无已发送/接受/已录用文案或事件；不能直接 `hired`。**证据：UI + API + DB**。

- [ ] **AC-27｜Offer 子状态与关闭合法性**（S）
  前置：`active/offer/preparing`、`active/offer/sent`、`active/offer/accepted` 及已关闭 Offer 申请。操作：请求非法 preparing→accepted、sent→hired、accepted→offer_declined、关闭后变更 Offer；另从 `preparing/sent/accepted` 分别执行企业终止或候选人退出。
  预期：非法请求被拒且不生成事件；`company_rejected/candidate_withdrew` 合法结束时保留最后 `preparing/sent/accepted` 和原因；`declined` 仅与 `closed/offer_declined` 同步成立。**证据：API + DB**。

### F. 历史、待办、迁移与安全（P0-08 / P0-09 / P0-10）

- [ ] **AC-16｜旧版历史不可伪造**（S）  
  前置：准备来自 V2.1.1 的 `rejected` 与 `offer` 记录。操作：在隔离环境迁移并查看详情。  
  预期：`rejected` 可表示结束/企业淘汰，但旧淘汰前阶段、实际原因、时间为未知而非凭空生成；旧 offer 不能自动标记 sent/accepted/hired；不会补造旧的面评或晋级事件。**证据：迁移报告 + UI + DB**。

- [ ] **AC-17｜当前阶段待办统计与来源可追溯**（M）
  前置：分别准备筛选、待安排、已完成未评、已完成已评、Offer 待处理的活跃申请，以及**上一阶段已带缺评理由晋级**的申请。操作：查看 Dashboard 和详情。
  预期：各项数量符合 `active + 当前 stage_scope` 口径、按面试/申请单位准确计数；旧轮次缺评仅留历史详情，不计“当前待面评”；操作入口能到来源对象。**证据：UI + DB/聚合**。

- [ ] **AC-28｜普通删除不破坏业务历史**（S）  
  前置：某申请有已完成面试、评价、阶段及结果事件。操作：尝试从普通管理页面删除申请或面试。  
  预期：不允许直接级联抹去关键证据；界面/接口显示明确限制或合法归档处理。**证据：UI + API + DB**。

- [ ] **AC-29｜同申请多份当前缺评与历史豁免不混算**（M）
  前置：R01 初面先后完成两场面试，两场均无评价，仍 `active/first_interview`；另准备两场缺评后已理由晋级复面的 R02。操作：核对待办和申请数。
  预期：R01 当前待面评为 2 个面试工作项、活跃申请为 1；R02 的两份旧轮次缺评仍在详情可追溯，但全局当前待面评对 R02 计 0；不计入已面评齐全。**证据：UI + DB/聚合**。

- [ ] **AC-30｜Dashboard 业务时区、时间边界与 Offer 待办**（M）
  前置：按 `Asia/Shanghai` 固定日期和时间，准备同日/跨日 `scheduled/completed/cancelled` 面试与 `preparing/sent/accepted` Offer 记录。操作：在当天 00:00、预约开始时间临界点和次日 00:00 检查统计，并登记 Offer 状态变化。
  预期：“今日面试”按 `[当天00:00,次日00:00)` 计数且按状态分类；预约到时提醒仅对到达 `scheduled_at` 的 `scheduled` 生效；Offer 任务随子状态变化、无重复申请计数。**证据：UI + 固定时钟 + API/DB**。

- [ ] **AC-31｜旧职位映射冲突与迁移回滚**（S）  
  前置：隔离旧库分别准备职位名唯一匹配、无匹配、同名多匹配数据。操作：运行经过总控批准的迁移流程，并模拟失败后回滚。  
  预期：唯一匹配才自动关联；歧义/无匹配有待核实标记，不猜测；记录数/外键核对清楚；失败后可从备份恢复原测试状态。**证据：迁移与回滚日志 + DB**。

- [ ] **AC-32｜认证与隐私边界**（S）  
  前置：有效 HR 账号、无 token/失效 token/未经允许角色的模拟请求。操作：分别访问业务写接口和事件历史；查看 Demo 数据。  
  预期：未认证拒绝；关键写操作有服务端资格校验；事件操作者不可由客户端任意冒充；演示数据为虚构、无生产密钥。**证据：API + DB + 代码/演示资料检查**。

### G. 总控 R1～R3 与时间口径补充案例（P0；原编号不变）

- [ ] **AC-33｜申请状态 / 阶段 / Offer / Outcome 合法性矩阵**（S）
  前置：准备四阶段的活跃记录及 Offer preparing/sent/accepted/declined 相关测试输入。操作：分别尝试：筛选/初面/复面直接关闭为 `hired` 或 `offer_declined`；`active + declined`、`active + outcome!=null`、`active + closed_at!=null`；`closed + outcome=null`、`closed` 但没有结束原因；非 Offer 阶段带非空 `offer_status`；`offer/declined` 组合 `company_rejected`；Offer 阶段在 `preparing/sent/accepted` 进行合法企业终止/候选人退出；`accepted` 后确认 `hired`。
  预期：**只有 PRD §4.1.1 规定的新数据组合可持久化**。所有非法组合即使绕过前端通用 PATCH 也被服务端拒绝且不产生事件；合法结束保留原阶段、Offer 最后状态、原因和服务端时间。**证据：API + DB + 事件记录**。

- [ ] **AC-34｜已提交面评的 P0 有痕误录更正**（S）
  前置：一场 `completed` 面试有有效评价、真实录入账号为 HR01。操作：尝试普通 PATCH 覆盖或无理由更正，再以合法 HR 账号提交“更正面评”，填写原因并改动评价结论/理由；最后在申请关闭后对既有面评进行有痕更正。
  预期：普通覆盖与空理由被拒；同场始终**恰好一份当前有效面评**；更正事件完整保存原始/新内容快照、实际操作人、服务端时间和原因，原 `submitted_at` 保留；详情能看到“已更正”和历史；关闭后更正不改变阶段、结果及既有决策。**证据：UI + API + DB + 历史**。

- [ ] **AC-35｜缺评晋级、旧轮补录和 Dashboard 不混算**（S）
  前置：初面 `completed` 但无面评，HR 已填写原因晋级复面（仍 `active`）。操作：核对晋级事件、复面 Dashboard 当前待面评数，在旧初面详情补录面评，再查询历史；另外准备一条已关闭、仍遗留旧轮缺评的申请，尝试在关闭后补交从未提交过的评价。
  预期：晋级事件始终保存当时的缺评和豁免原因；缺评未补录时在详情显示“历史缺评（已说明原因推进）”，**不计新阶段的当前待面评**；活跃时可按原轮次补录，显示实际提交账号/时间与“晋级后补录”，不回填历史提交时间、不改变原阶段决策；已关闭后新补录被拒，旧缺评仍可查。**证据：UI + API + DB/聚合**。

- [ ] **AC-36｜预约到时提醒的精确时间边界**（M）
  前置：业务时区 `Asia/Shanghai`；固定 `scheduled_at = 2026-11-03 14:00:00+08:00` 且 `status=scheduled`。操作：分别令时钟为 13:59:59、14:00:00、14:00:01，并对 `completed/cancelled` 同时点的记录检查提示。
  预期：**13:59:59 不提示，14:00:00 开始提示，14:00:01 继续提示**；仅 `scheduled` 提示“预约开始时间已到，待确认面试状态”，不使用不存在的结束时间，不自动生成 `completed_at` 或状态完成事件；时间换算与 Dashboard 一致。**证据：固定时钟 + UI + DB**。

## 四、必须执行的端到端演示（DEMO-E2E-01）

- [ ] 新建开放职位并录入一个虚构候选人的职位申请。
- [ ] HR 正常通过筛选，进入初面；安排一场面试并改期一次。
- [ ] 标记初面已完成；验证阶段仍为初面；录入面试官推荐与理由。
- [ ] HR 查看面评后晋级复面；记录中能看到真实阶段事件。
- [ ] 复面完成但无评价；HR 收到缺失提示，填写原因后晋级 Offer；晋级事件保留缺评 ID 与说明，旧阶段缺评只在历史提示，不计当前阶段待面评。
- [ ] 在 Offer 阶段依次确认未发送、已发送、候选人接受；此时申请仍为 active，暂不执行最终录用确认。
- [ ] **在 HR 最终确认录用、申请仍 active 时**，从原复面面试补录原先缺失的评价；验证实际补录时间、原缺评豁免事件保留、不反转晋级事实。
- [ ] HR 确认录用后，检查申请已关闭、outcome=hired、阶段仍为 offer；查看真实操作历史，并核对 Dashboard 的申请数、当前面评工作项、Offer 工作项和录用口径与数据库一致。

**辅助演示（DEMO-E2E-02）**：两条同名职位分开统计；候选人自愿退出、企业淘汰、Offer 拒绝分别结束，保持结果和阶段信息。
