## 2. IA v0.1：导航与实体语义

### 2.1 顶级导航（尽量复用旧系统）

```text
HireFlow
├─ 工作台（Dashboard；一级业务导航）
│  ├─ 业务指标（按记录与活动单位说明）
│  ├─ 待办类型：待筛选 / 待安排 / 到时待确认 / 待面评 / 待决策 / Offer 待处理
│  ├─ 对应来源记录快速入口
│  └─ 今日面试 + 轻量辅助统计
├─ 职位管理（Position；一级业务导航）
│  ├─ 职位列表：搜索、状态筛选、开放/关闭、编辑
│  └─ 关联申请快捷入口（按 position_id 过滤）
├─ 候选人管理（一级业务导航；UI 名称保留，业务记录是 CandidateRecord）
│  ├─ 申请记录列表：搜索、职位/阶段/生命周期/当前待办筛选
│  └─ 候选人详情（某个职位申请的业务枢纽）
│     ├─ 申请概览 + 当前任务/HR 决策
│     ├─ 本阶段面试与评价
│     ├─ Offer 记录（仅在 Offer 阶段展示）
│     ├─ 资料/备注
│     └─ 真实事件历史与旧轮次缺评
├─ 面试管理（Interview；一级业务导航）
│  ├─ 面试列表：时间/阶段/活动状态/待面评
│  └─ 面试操作：预约/改期/完成/取消/面评/更正 → 关联申请详情
└─ 个人中心（账号入口，非第五个招聘业务模块）
   └─ 资料与密码
```

**Owner 确认（Q3）：** 保留上述四个一级**业务**模块，导航侧栏可展开以显示文字；个人中心作为账号入口保留。面评、Offer、活动历史是申请/面试关联的子视图或动作，不新建业务顶级模块。导航名称沿用“候选人管理”，但申请统计必须写“申请记录数”，同一自然人两岗是两条记录（PRD §4）。全局多标签页属于工作区导航辅助层（Q4），不是第五个模块。

### 2.2 单一上下文来源原则

- 从“待面评”进入时：先定位**具体 Interview ID**，附带候选人 + 职位 + `stage_scope`，回到候选人详情时仍对应同一 CandidateRecord。
- 从“待决策”进入时：定位**具体 CandidateRecord ID**，展示本轮面试及评价，不把推荐通过自动映射为 HR 决策。
- 从职位进入申请列表：按稳定 `position_id` 过滤，名称相同的职位要有部门/ID 等消歧信息；不能用职位 title 作为链接键。
- 时间展示与“今日”按 `Asia/Shanghai`；预约到时仅提示确认状态，不自动完成面试。

## 3. 全局 Shell 低保真（已按 Q3、Q4 确认）

```text
┌─ 左侧业务导航（默认可展开文字／折叠显示图标与提示） ──────────────────────┐
│ HireFlow    │ 顶栏：面包屑／页面上下文                      当前 HR 账户 │
│            ├──────────────────────────────────────────────────────────┤
│ 工作台      │ 全局多标签页： [工作台] [候选人列表 ×] [李华·详情 ×]       │
│ 职位管理    ├──────────────────────────────────────────────────────────┤
│ 候选人管理  │ 页面标题 + 必要说明                       主要页面操作    │
│ 面试管理    │ ┌──────────────────────────────────────────────────────┐ │
│            │ │ 页面内容：工作项／列表／候选人详情／面评等             │ │
│ [账号入口]  │ │ 筛选与反馈状态：Loading／Empty／Error／Retry          │ │
│            │ └──────────────────────────────────────────────────────┘ │
└────────────┴──────────────────────────────────────────────────────────┘
```

**已确认：** 侧栏支持展开文字（Q3）；**全局多标签页保留并简化（Q4）**。建议只保留一条清晰的全局页签行，展示可辨识的模块名或候选人详情名称；避免页签、面包屑和页面大标题三处重复强调同一信息。主业务导航不再新增层级。

**实现前须验证的 UI 行为（留 D1-02/E2）：** 原有多标签页的固定首页、关闭/切换与动态标题行为可作为复用基线，但不能假设现版已具备页面缓存或筛选条件永久保留；需要设计切换后的状态恢复及可能丢失的未提交表单提示，不将这些未经验证的能力写为已实现。对候选人详情采用页内分区或锚点辅助定位，不再引入多个与全局页签重叠的主业务 Tabs。浅色为视觉优先参考，精确组件尺寸、配色和断点留 D1-02。


## 4. 核心页面结构及业务映射

### 4.1 Dashboard｜指标在上、任务突出、图表辅助（Q2 已确认）

```text
┌ 工作台 ─────────────────────── 当前业务日期／时区提示 ────────────────────┐
│ [开放职位数]       [活跃申请记录数]      [今日面试数(状态拆分)]            │
│                                                                        │
│ 需要处理的工作                                                         │
│ [待筛选(申请)] [待安排(申请)] [到时待确认(面试)]                         │
│ [待面评(面试)] [待决策(申请)] [Offer 待处理(申请)]                        │
│                                                                        │
│ [对应工作项列表：类型 / 申请 / 职位 / 预约或最近时间 / 前往处理]          │
│                                                                        │
│ [今日面试：预约开始时间与当前状态] [辅助指标/图表：真实数据有效才显示] │
└────────────────────────────────────────────────────────────────────────┘
```

- **Owner 确认（Q2）：** 从上到下严格按 **指标 → 待办 → 具体工作项 → 今日面试 → 辅助图表** 排布；指标只占紧凑的首行，不能以大图表挤占工作项，也不能擅自将待办排到指标上方。今日面试数及状态分组按 PRD 定义。
- R：六项待办各自有严格口径，不能合为含糊“待处理人数”；例如待面评按**当前轮次已完成、无有效面评的面试记录数**，同一申请两场缺评计两项；历史豁免缺评不进入此项（§5.8；AC-17/29/35）。
- R：待安排仅按当前初/复面无 `scheduled`、无 `completed` 的活跃申请记录计算，取消不等于完成；待决策需要有完成面试且全评齐、无 `scheduled`。没有已完成面试而允许理由推进的特殊场景可从详情进入，但不能擅自计入已冻结的“待决策”。
- R：`now >= scheduled_at && scheduled` 仅出现“预约开始时间已到，待确认面试状态”；不可依据时间将 Interview 自动设为完成（§5.3、§5.8；AC-21/36）。
- D：工作项列表与上方数量卡是同一真实来源对象的两种入口；卡片跳至带筛选的列表/具体对象，不新建 Task 表或消息通知系统。
- D：原版零值趋势大图可降级为下方辅助模块；不做未获 P1 批准的招聘漏斗和周期统计。

### 4.2 职位管理｜稳定 ID 与关联保护

```text
[职位管理]                                    [+ 新增职位]
[名称搜索]  [开放/关闭筛选] [部门（如有）]
[职位名称 + 部门/识别ID | 状态 | 申请总记录数 | 活跃申请数 | 操作]
[查看关联申请] [编辑] [关闭/开放] [更多：删除（有保护）]
[分页 / 搜索为空 / 无数据 / 加载失败]
```

- R：职位可以同名，关联按 `position_id`；关闭职位不得静默结束已活跃申请，新申请不能默认关联关闭职位；有历史关联不能无提示硬删除（§5.1；AC-01/02/03/19）。
- D：同名显示“标题 + 部门/职位标识”以消歧，申请总数与活跃数要标单位；不新增完整职位详情页作为 P0 必做。

### 4.3 申请列表｜以扫视和下一步为中心

```text
[候选人管理 / 申请记录]                         [+ 新增申请]
[姓名或职位搜索] [职位] [阶段] [进行中/已结束] [当前工作类型]
[姓名/申请标识 | 应聘职位 | 阶段 | 生命周期/结果 | 当前待办 | 负责人 | 投递日期 | 操作]
[姓名 → 详情]                                          [查看] [更多]
[分页 / 空态 / 错态 / 重试]
```

- R：阶段只能四选一，结束结果/是否活跃另显示；“已淘汰”不是阶段。Offer 非终止时需标明子状态；一个人投两岗是两条申请记录（§4/§7；AC-10/11/18/33）。
- **Owner 确认（Q5）：** 列表采用中等密度；优先展示姓名、职位、阶段、生命周期/结果、当前待办及负责人等可扫视信息；罕用动作收进“更多”，避免行内挤满彩色文字按钮，具体列宽与行高留 D1-02。
- D：将危险删除收进“更多”，有已发生历史时禁止普通清除；避免每行同时暴露多个危险彩色文字按钮。
- D：当前待办只是从已冻结业务事实派生的阅读/筛选标签，不新增 `task_status` 业务状态字段。

### 4.4 面试管理｜状态与下一动作分离

```text
[面试管理]
[搜索] [预约日期] [面试状态: scheduled/completed/cancelled] [阶段] [待面评]
[预约开始时间 | 候选人+职位 | 轮次 | 面试官姓名 | 面试活动状态 | 当前工作提示 | 操作]
[预约到时提醒 ≠ 已完成]
[安排/改期/完成/取消] 或 [填写面评/查看面评/更正面评] → [申请详情]
```

- R：仅 `scheduled` 可改期、完成、取消；取消需原因。单申请任一时刻 P0 最多一场 `scheduled`，同阶段可顺序多场；活动状态不包含“待面评/待决策”（§5.3；AC-09/21/22/36）。
- **Owner 确认（Q5）：** 面试列表采用中等密度：完整保留预约开始时间、候选人/职位、轮次、面试官、真实活动状态和下一动作；密度不能以隐藏关键状态和错误合并状态为代价。
- D：列表用日期 + 活动状态 + 下一动作识别，避免把 `Waiting on Feedback` 错当 Interview.status 的新枚举；时间展示指预约开始时间，不能显示不存在的结束时间。

### 4.5 面评表单与更正入口｜聚焦事实

```text
[为某场已完成面试填写评价]
[只读上下文：候选人、职位、面试 ID、初面/复面、实际完成状态]
[专业评价人姓名]   [推荐结论: 推荐通过 / 不推荐通过 / 暂不确定]
[评价依据（必填）]
[说明：实际录入人 = 当前登录 HR]
[取消] [提交评价]

[已提交 → 更正面评（不是普通编辑）]
[原评价的只读摘要] [更新后的评价人/推荐结论/依据] [更正原因（必填）]
[保存更正] → 保留原始 submitted_at、原/新快照、当次真实操作账号与时间
```

- R：每场最多**一份当前有效面评**；首次提交仅对 `completed` 且处于允许录入条件的申请。专业评价人 `reviewer_name` 与实际登录 HR 不是同一个身份概念（§5.4；AC-23/24）。
- R：已提交评价即使招聘阶段已晋级或申请已关闭也可**有痕纠错**，不得触发逆转原决策；已关闭不得**新增**从未提交的缺评（§5.4/5.5；AC-20/34/35）。
- D：不引入 P1 评分维度、多评价人并行、审核流或任意覆盖功能。更正后提供“已更正”与历史快照入口，呈现更正发生于原决策之后的事实（如属实）。

### 4.6 全局多标签页的保留与简化（Q4 已确认）

- **保留：** 当前已存在的全局页面标签（固定工作台及业务列表/详情切换等），让 HR 同时查看职位、申请和面试；这是既有 UI 能力的组织优化，不是新增业务模块。
- **简化：** 同时只显示一条全局标签带；避免标签名称长、重复导航文案、候选人详情产生多个难区分的同名页签。按现有身份与申请语义区分不同申请的详情标题（具体标识方案留 D1-02）。
- **不扩范围：** 不把保存所有表单输入、浏览器关闭后自动恢复所有筛选等当作已冻结 P0；需核对真实现有能力。对于尚未保存的面评/更正表单，切换或关闭页签的防误失提示属于交互设计需验证的细节。
- **与详情结合：** 详情主区仍用方案 A 的信息分区，不能叠加另一套复杂内层 Tab 导致“先切全局页签，再切详情页签”才能找到 HR 决策。

## 5. 候选人详情｜方案 A 已由 Owner 确认（Q1）

### 采用方案 A：任务主区 + 资料辅助栏 + 真实历史

```text
[返回申请列表]  姓名 · 应聘职位/申请标识  [当前阶段] [进行中/已结束]
             [关键操作：本阶段下一动作 / 进入下一阶段 / 结束招聘]
[四阶段只读位置：筛选 — 初面 — 复面 — Offer]  （不作为真实事件时间线）
┌────────────────────────── 主要业务工作区 ────────────────┬── 资料辅助栏 ───┐
│ [当前待办 / 决策说明 / 预约到时状态]                      │ [申请摘要]           │
│ [当前阶段面试（可多场，按场次显示）]                       │ [联系方式/学历/经历] │
│ [每场活动状态 + 评价 + 补录/有痕更正操作]                 │ [负责人/备注]        │
│ [Offer 状态与操作（仅 Offer 阶段）]                       │ [结束结果与原因]     │
│ [真实历史：时间 / 实际操作者 / 事件 / 原因 / 快照链接]     │                      │
│ [旧轮缺评已说明原因推进 / 旧版历史未知明确区分]           │                      │
└───────────────────────────────────────────────────────┴──────────────────────┘
```

**Owner 确认：** 用同页的“当前任务 → 当前阶段面试/面评 → Offer（如适用） → 真实历史”组织业务主区，候选人/申请基础资料放在侧栏。这样 HR 可以在决策前看到依据，减少跨页面切换。信息密度为中等；历史较长时可增加页内定位/局部折叠，具体滚动和侧栏响应式方案留 D1-02。线框中的主次面积仅为布局关系，不承诺固定 2/3 或 1/3 像素比例。

**必须区分：** 顶部四阶段只是当前/最后阶段的只读位置指示；下方“真实历史”只能呈现服务端保存的真实业务事件。`offer/preparing` 只能写准备中；`offer/accepted + active` 不得写已录用。旧轮次缺评豁免在历史显示，不重新计入当前阶段待面评。

### 已比较但本次不采用的方案 B：工作区 Tabs + 持续资料侧栏

```text
[姓名 / 申请识别 / 当前阶段 / 生命周期 / 决策操作]
┌─ 当前任务 | 面试与面评 | Offer（仅 Offer 阶段） | 活动历史 ─┬─ 概况侧栏 ─┐
│ 主 Tab 中的当前内容                                           │ 资料摘要   │
│ 需要切 Tab 才能分别看到完整决策证据与操作历史                  │ 当前状态   │
└──────────────────────────────────────────────────────────────┴────────────┘
```

**优点（D）：** 长历史信息可减少单次滚动，适合资料量扩大。**风险（D）：** 面评、历史、决策分散在多个 Tab 中，可能提高 HR 的切换成本；同时“Offer”只应在 Offer 阶段出现，不应暗示所有阶段均可操作。

**Q1 定点结论：方案 B 未被选用。** 保留这一段是为了说明取舍理由，不应在 D1-02 默认把主要业务拆成“当前任务／面试／Offer／活动历史”四个内嵌 Tabs。允许研究方案 A 的页内锚点，但不得因全局多标签页（Q4）而变回方案 B。D1-02 再决定精确布局比例、移动端折叠逻辑和组件。

### 5.1 详情特殊场景必须可读

| 场景 | 显示与可用动作（依冻结 PRD） |
|---|---|
| `active/first_interview`，已预约 | 显示“已安排面试”，可以改期/完成/取消；**不能绕过预约直接晋级** |
| 已完成面试但未交面评 | 显示当前缺评清单；可填面评；HR 若理由晋级须记录缺失 ID 和原因 |
| 初面缺评已说明理由晋级复面 | 历史明确写“初面缺评，已说明原因推进”；**不计入复面当前待面评**；仍 active 时仅符合要求的旧轮次可补录 |
| `completed` 且已提交面评 | 展示推荐结论和专业评价人 + HR 录入账号；有独立“更正面评”入口及前后快照 |
| `offer/preparing` | 只显示“Offer 准备中”与“登记已发送”；**不写已发放、已录用** |
| `offer/sent` | 可登记接受/拒绝；拒绝时与关闭及事件同步 |
| `offer/accepted` 且 `active` | 显示“候选人已接受，待 HR 确认录用”，不能提前统计 `hired` |
| `closed/hired` | 保留 `offer/accepted` 与结束事实；不再执行普通招聘动作；仍可对已存在面评进行有痕更正 |
| 旧版历史不可确认 | 明确“旧版记录，阶段/事件/Offer 事实未知或待核实”，不得生成完整绿色成功时间线 |

### 5.2 详情动作的显隐与异常反馈

- **推进 / 结束 / Offer 操作**只在冻结 PRD 的合法阶段和申请状态下提供对应入口；有 `scheduled` 时阻止晋级/关闭并指向“先完成或取消面试”。不支持任意跳轮、回退或关闭后恢复。
- **面评提交与更正**必须是不同动作。更正入口不仅展示“已更正”，还可查看更正前后快照、实际操作者、时间、理由；即使申请关闭也允许既有评价的合法有痕更正，但禁止首次补录缺评。
- **异常与旧数据**展示可理解的拦截/冲突、重新加载、旧版未知事实和缺失数据说明；不得在失败后提前显示晋级成功。
- 以上为已冻结业务规则对应的设计表达，不新增接口路径或数据库字段；精确组件与禁用态文案由 D1-02 深化。

## 6. HR 核心操作路径（低保真）

### 补充路径 P-00｜待筛选到安排面试（原 v0.1 页面语义的显式串联）

```text
工作台「待筛选（申请记录数）」→ 带当前任务筛选的候选人列表
→ 进入某条 CandidateRecord 详情 → 查看该职位的申请资料
→ HR 明确确认筛选通过：screening → first_interview（真实阶段事件）
→ 本阶段尚无 scheduled/completed 面试，显示待安排入口
→ HR 安排当前轮次第一场面试（预约开始时间、面试官）
→ 面试活动变为 scheduled，但阶段仍为 first_interview
```

对应 PRD §4.2、§5.1～5.3、§5.8、DEMO-E2E-01；关联验收可参看 AC-01/17/22（不将 AC-04/06 错用作筛选进入初面的直接证据）。筛选结果与预约是不同业务动作；新申请必须选开放职位的稳定 ID。

### 路径 P-01｜正常：从待面评到 HR 决策

```text
Dashboard「待面评（面试工作项）」
→ 按 Interview ID 定位已完成、当前轮次的面试
→ 填写专业评价人 + 推荐结论 + 非空依据；HR 账号真实留痕
→ 显示“评价已提交”，**申请阶段不变**
→ 返回该 CandidateRecord 详情，查看所有当前轮次面试及评价
→ 若无 scheduled 且条件满足，HR 明确点击“进入下一阶段”
→ 确认合法目标（初面→复面 / 复面→Offer）
→ 后端成功后刷新当前阶段与真实事件；冲突则提示并重新加载
```

对应 PRD §4.2/§5.4；AC-04/05/06/14/15/23/24。

### 路径 P-02｜例外：缺评说明理由晋级、随后旧轮补录

```text
详情「当前轮次完成面试仍缺面评」
→ HR 点击“进入下一阶段”
→ 风险确认：列出缺失面试 ID/轮次，原因必填；如仍有 scheduled 则阻断
→ 提交后晋级：事件保留旧阶段、缺评快照、理由、HR 账号、服务端时间
→ 旧轮缺评只留在详情历史，不再计当前阶段待面评
→ 申请仍 active 时，从旧轮历史进入“补录面评”
→ 记录真实补录时间，原特殊晋级事件不改变
→ 若申请 closed，则禁止首次补录；已提交面评仍允许有痕更正
```

对应 PRD §5.5/§5.8；AC-07/25/29/35。

### 路径 P-03｜Offer：记录事实到确认录用/拒绝

```text
复面 HR 决定晋级 → active/offer/preparing
→ HR 登记线下已实际发送 → active/offer/sent
→ 候选人接受 → active/offer/accepted
→ （仍 active，合法旧轮补录须在最终关闭前完成）
→ HR 单独确认录用 → closed/offer/accepted/hired

另一分支：active/offer/sent → 候选人拒绝并填写原因
→ 原子产生 closed/offer/declined/offer_declined + 事件
```

对应 PRD §4.1.1/§5.6；AC-12/13/26/27/33/35。不可将“进入 Offer”或“已接受”显示为已录用。

### 路径 P-04｜预约到时提醒

```text
Dashboard / 面试管理 → scheduled 且 Asia/Shanghai 当前时刻 >= scheduled_at
→ 提示“预约开始时间已到，待确认面试状态”
→ HR 核对实际情况后手动“完成”或“取消（填原因）”
→ 不自动生成 completed_at，不自动晋级，不自动认定面评
```

对应 PRD §5.3/5.8；AC-21/30/36。

### 补充路径 P-05｜已提交面评的有痕更正与事件历史

```text
面试管理或申请详情 → 已提交面评 → 点击「更正面评」
→ 查看当前有效内容，输入新评价人／推荐结论／依据 + 非空更正原因
→ 保存后仍仅一份当前有效评价，保留首次 submitted_at
→ 详情显示「已更正」，真实历史展示原/新完整快照、HR 账号、服务端时间和更正理由
→ 若更正在既有晋级/关闭之后发生，只记录纠错事实，不回退阶段或修改历史决策
```

对应 PRD §5.4/§5.7；AC-20/23/24/34。对从未提交的历史缺评，申请已关闭时不可走“首次补录”路径。

## 8. 交互和视觉约束（D1-01 原则，不是 D1-02 像素规范）

- **Owner 视觉方向**：A 现代简洁型 SaaS 主导全站，C 只强化关键招聘运营区域；**中等信息密度（Q5）**，尤其确保筛选与表格不拥挤。
- **全局视觉**：浅色优先，白/中性背景，有限强调色；Typography 与层级比装饰优先。侧栏与内容区层次清楚，避免旧版所有页面都像“同一套表格卡片”。
- **C 风格局部应用范围**：候选人列表、面试列表、当前工作项、真实活动历史；以分组、优先级和明确标签提升扫视效率，不追求极限行数；详情页主结构保持稳定清爽，面评表单低干扰。
- **状态辨识**：阶段、申请生命周期、面试状态、面评推荐、当前待办、Offer 子状态分别用文案/分组/必要标签识别，不能只靠颜色。`已更正` 是事件提示，不是新的面评结论。
- **操作安全**：推进、关闭、Offer 拒绝、面评更正等明确后果；并发/网络失败不可乐观伪装成功。普通删除不能抹去历史。
- **过渡和反馈**：保留 Loading/Empty/Error/Retry、表单校验、不可操作原因提示、服务器冲突后的重新加载；0 个当前待办表达“暂无当前待办”，不是凭空补案例。
- **旧数据**：未知事实必须显示未知；不能将旧 rejected 伪造成已完成筛选/初面/复面时间线，不能将旧 Offer 自动标成已发送。
- **实现边界**：暂不决定路由 URL、精确栅格/断点、组件原型和数据库物理结构；这些后续由 D1-02 / A 的 E2-01 处理。
