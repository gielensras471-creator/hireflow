# HireFlow V3.0｜02 竞品研究（S1-01 待验收稿）

> 研究日期：2026-10-30  
> 责任对话：02｜V3.0 产品研究与需求分析  
> 研究对象：飞书招聘、Greenhouse Recruiting、Ashby  
> 目标产品：小型企业／小规模招聘团队使用的招聘流程协作平台；HR 为主要用户  
> 状态：**研究完成，等待 01｜项目总控依据 S1-01 验收**；非 PRD、非 MVP 冻结、非竞品复刻规格。

## 0. 范围、方法与证据规范

本报告回答：**谁使用竞品、处理什么工作、如何管理招聘阶段／面评／决策／待办，以及哪些机制值得 HireFlow 借鉴？** 不开展 UI 视觉复刻，不比较价格，不把完整商业 ATS 的功能视为个人项目的必做范围。

标记：
- **F（产品事实）**：可从官方手册或帮助中心核验，紧随来源编号；这些是产品功能描述，不保证所有企业配置相同。
- **I（研究推断）**：从事实和招聘工作流程推导的解释，**不是用户访谈结果**。
- **P（HireFlow 建议）**：本项目的研究性候选方案，未获正式 PRD 批准的不得直接实施。

检索与复核时间：2026-10-30。优先查官方文档；未对三家产品进行付费账户实操、用户访谈或定量比较。没有收集或归档带个人信息的竞品截图；后续 UI 研究另行开展。

## 1. 飞书招聘：以任务和企业内协作为中心

### 1.1 事实卡

| ID | F｜官方事实 | 依据 |
|---|---|---|
| FS-01 | 飞书招聘员工工作台提供“我的面试”“我的任务”；任务示例包括简历评估、面试评价、Offer 审批；参与者可按权限查阅候选人信息。 | [S01] |
| FS-02 | 面试官可从日历或“我的面试”进入被分配的面试，查看候选人信息，并在面试后提交面评。 | [S01] |
| FS-03 | 官方自助约面场景包含评估、发出可约时间、候选人确认时间和评价等动作。 | [S01] |
| FS-04 | **集中面试这一特定场景**下，候选人状态包含“待安排”“等待面试”“面试中”“待确认面试结果”等；HR 可以按面评决定进入下一轮或结束本场面试。 | [S02] |
| FS-05 | **集中面试这一特定场景**支持配置自动进入下一轮或结束面试。由此不能推断“所有飞书招聘面试都会自动晋级”。 | [S02] |

### 1.2 分析与取舍

**I：** 招聘涉及跨角色交接；HR 需要看“现在是谁该做什么”，不能仅用候选人处于“初面”描述任务进度。部分企业会用人工确认推进，部分场景有自动化能力；模式依具体场景而异。

**P：** 借鉴“当前待办、待面评、待决策”的任务语义；HR 为主要操作人，面试官／用人经理是协作角色。**不借鉴**飞书生态聊天、Bot、日历联动、视频面试、审批引擎或自动流程配置作为 V3.0 当前目标。

## 2. Greenhouse：结构化评价、明确决策与任务分配

### 2.1 事实卡

| ID | F｜官方事实 | 依据 |
|---|---|---|
| GH-01 | Greenhouse 使用职位相关的 Scorecard，通过预设能力维度记录面试反馈；总体推荐意见可以是 Definitely Not、No、Yes、Strong Yes，也允许 No decision。 | [S03] |
| GH-02 | Scorecard 可以按配置为非必填；面试反馈与职位申请的 Advance / Reject 操作是不同动作。 | [S03][S04] |
| GH-03 | 申请审核中，具备权限的人可推进或拒绝候选人；拒绝流程要求选择原因。 | [S04] |
| GH-04 | 面向招聘团队角色有自动分配的任务，如安排面试、完成用人经理审核、面评齐全后决定推进／拒绝。 | [S05] |
| GH-05 | Candidate Activity Feed 保留候选人层面的重要操作、备注和面评等活动（具体可见范围受权限影响）。 | [S06] |
| GH-06 | 已提交面评可在组织配置允许时修改；修改后的面评会有编辑标识。 | [S07] |

### 2.2 分析与取舍

**I：** 面试官的推荐意见是决策输入，不是不可逆的候选人晋级指令。面评若没有结构化字段，决策将缺少解释依据；如果强制每份面评都齐全，特殊招聘流程可能被阻塞。

**P：** 借鉴最小面评：评价人、提交时间、总体推荐、依据/备注，并研究“未齐评价可说明原因推进”的柔性校验。借鉴关键历史与待办推导。**不借鉴**复杂 Scorecard 模板编辑器、全套招聘团队岗位权限、全量审计平台。

## 3. Ashby：阶段、活动进展与职位申请分别表达

### 3.1 事实卡

| ID | F｜官方事实 | 依据 |
|---|---|---|
| AS-01 | Interview Plan 定义岗位招聘阶段；Interview 和 Feedback Form 是不同对象，后者用于提交评价。 | [S08][S09] |
| AS-02 | Candidate Activity Statuses 提供 Needs Scheduling、Scheduled、Waiting on Feedback、Needs Decision 等表示当前下一步工作的状态。 | [S10] |
| AS-03 | 在 Ashby 的说明中，已预约的面试时间过去后，活动可能进入 Waiting on Feedback；取消已预约面试可能回退为 Needs Scheduling。该机制**不证明面试实际发生过**。 | [S10] |
| AS-04 | Candidate Pipeline 按职位的 job considerations 展示申请；状态提示和任务进展并不等于自定义招聘阶段本身。 | [S11] |
| AS-05 | 候选人可以被考虑到多个职位；官方区分“将已有申请转到另一个岗位”和“新增另一岗位的考虑记录”。 | [S12] |
| AS-06 | Interview Plans 的完成部分区分 Archived 和 Hired；Offer 相关活动另有需要审批、等待接受等过程状态。 | [S08][S10] |

### 3.2 分析与取舍

**I：** “张三处于初面”无法表达是否待安排、已预约、待面评还是待招聘决定；同一候选人在不同职位可能拥有独立结果。进入 Offer 阶段不等于 Offer 已发送，也不等于已录用。

**P：** 借鉴“阶段／活动进度／结果”分离，以及每个职位申请独立生命周期的**概念**。但**独立 Application 数据表尚未确定**：最小模型 A+ 同样可以正确表达单岗位申请，详见 `HireFlow_R04_数据模型A_B对比研究.md`。

## 4. 横向比较：围绕 HR 的日常工作，而非功能榜单

| 研究问题 | 飞书招聘 | Greenhouse | Ashby | HireFlow 的待研究方向 |
|---|---|---|---|---|
| 谁在使用？ | HR、面试官、招聘参与者 | 招聘团队、面试官、用人经理等 | 招聘团队与不同权限用户 | **已确认 HR 主导、其他角色协作** |
| 当前工作在哪里？ | 工作台的我的面试／我的任务 [FS-01] | Dashboard 上的角色任务 [GH-04] | Pipeline 的活动状态 [AS-02] | 从业务数据导出待筛选／待安排／待面评／待决策 |
| 如何表示面评？ | 具体面试后的评价 [FS-02] | Scorecard 和推荐意见 [GH-01] | Feedback Form [AS-01] | 评价事实与招聘决策分离 |
| 如何晋级／终止？ | 集中面试可人工确认或开启特定自动操作 [FS-04/05] | 权限下的推进／拒绝动作 [GH-03] | Pipeline 阶段和活动分离 [AS-02/04] | 默认由负责人决策，不由面试结束直接晋级 |
| 如何追溯？ | 工作台提供任务进度 [FS-01] | Activity Feed [GH-05] | 职位申请保留历史信息 [AS-05] | 关键事件真实记录，不凭当前阶段倒推 |
| 多岗位同一人？ | 本轮未核实足够细节，**不做断言** | 本轮未细查完整跨岗位结构，**不做断言** | 明确支持不同 Job Consideration [AS-05] | A+/B 数据模型待确认 |

> **注意**：此表是对本报告选定场景的“研究观察”，不代表各平台完整能力排名，也不能据此宣称某产品“不支持”未列出的能力。

## 5. 对 HireFlow 的候选需求：价值与边界

| 候选能力 | 产品理由（I/P） | V3.0 研究态度 | 证据或依赖 |
|---|---|---|---|
| 面试完成、面评与招聘决策独立 | 否则评价依据和阶段含义混乱 | 高优先讨论 | GH-01/03，AS-02，现有源码问题 |
| HR 明确执行推进／终止并留理由 | 让决策责任可追溯 | 高优先讨论 | GH-03/05；已确认原则 |
| 缺失面评提醒与理由推进 | 兼顾规范与特殊情况 | **研究原则已确认，字段未冻结** | DEC-R02-01，GH-02 |
| 可靠的岗位关联与人数口径 | 避免同名岗位和假计数 | 高优先讨论 | 旧源码核验，非竞品直接推导 |
| 面试取消、改期、评价延迟 | 面试是独立活动，不等同阶段 | 高优先讨论 | AS-03 |
| 从事实推导 HR 待办 | 避免待处理任务遗漏 | 讨论简化实现 | FS-01，GH-04，AS-02 |
| 结构化面评模板编辑器 | 真实企业可以需要，但个人项目成本高 | 暂不优先 | GH-01，AS-01 |
| 完整审批、多租户、复杂 RBAC、第三方日历、AI | 超过已冻结产品边界 | **总纲明确不做** | 主控总纲 §1.4 |

## 6. 已确认、未确认与证据局限

**已经由用户确认的研究方向**：
1. `DEC-R01-01`：将招聘阶段、面试状态、面评、招聘决策区别表达。
2. `DEC-R02-01`：面评未齐时可提示风险并允许说明原因后推进，必须保留此特殊操作记录。
3. `DEC-R03-01`：以 HR 为主要用户，兼顾面试官和用人经理。
4. 项目总方向：保留企业招聘流程协作平台，不转型为个人求职工具。

**尚未确定**：正式 MVP 必做清单、招聘生命周期精确枚举、是否为 Application 独立建表、Offer 模型粒度、面评人数与模板结构、权限实现细节、全部异常场景的实际范围。

**研究局限**：
- 主要依据厂商官方功能文档，可信地描述“软件提供什么”，不能替代 HR 深度访谈说明“用户多大程度需要”。
- 官方文档涉及套餐、产品版本与组织配置差异；勿将特定配置推广为强制产品规则。
- 未开展竞品实际账号验收、真实用户访谈、真实招聘数据统计；无独立用户痛点样本。
