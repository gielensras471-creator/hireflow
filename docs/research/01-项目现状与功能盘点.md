### 2.2 Router、Pinia、Axios 的关系

```text
main.ts → 注册 Pinia、Router、Element Plus → App.vue / RouterView
Router.beforeEach → getSession（浏览器本地会话及 expiresAt）
  ├─ 公开页：登录 / 404
  └─ 受保护页 → AppLayout → 业务页面
业务页面
  ├─ 候选人 / 面试 / 资料 → Pinia action → 资源 API 模块
  └─ 职位 / Dashboard → 资源 API 模块（页面 ref 保存数据）
API 模块 → request.ts / Axios → getSession → Bearer Token → Express
响应 → API 返回值 → Store 或页面 ref → computed / 模板
401 → clearSession → 浏览器跳转登录页（携带 redirect）
```

Router 负责导航和前端入口限制；Pinia 保存前端共享状态，不是数据库；Axios 负责请求与会话头部。登录 Token 保存在 `src/utils/auth.ts` 管理的 storage 中，没有 auth Store。`getCurrentUserApi()` 已封装 `/auth/me`，当前登录后实际调用的是 `profileStore.fetchProfile(true)` → `/profile`。

证据：`src/router/{index,routes,guards}.ts`、`src/api/request.ts`、`src/utils/auth.ts`、`src/stores/*.ts`、`src/views/login/components/LoginForm.vue::submit`。

### 2.3 Express、SQLite 与交互流程

```text
server/index.js 导入 database.js
  → 解析数据库路径 → 打开 DatabaseSync → WAL / foreign_keys
  → CREATE TABLE IF NOT EXISTS / 索引 → 满足空库条件时 seedDatabase()

HTTP → CORS → express.json（1mb）
  ├─ GET /api/health：公开
  ├─ /api/auth → POST /login：公开；GET /me：路由内 requireAuth
  └─ /api → requireAuth → profile / positions / candidates / interviews
      → 参数检查 → db.prepare(...).get/all/run
      → JSON 或 204 → Axios → 页面更新
未匹配请求 → notFound；异常 → errorHandler → HTTP 状态与 message
```

数据库只定义四张表：`users`、`positions`、`candidates`、`interviews`。面试以 `candidate_id` 外键关联候选人并级联删除；职位与候选人没有 ID 外键。路由通过 SQL 别名把 `candidate_id`、`applied_date` 等转换为前端 camelCase。`db.transaction(callback)` 是本项目添加的 BEGIN/COMMIT/ROLLBACK 包装；职位改名、候选人增删改等部分操作使用它，不能据此认为前端多个请求具有同一事务。

`database.js` 顶层有创建目录、建表和种子操作，因此本次只读取文本，没有 import/执行任何服务器模块。种子只在四张表都为空时插入，不是每次启动都覆盖数据，也不是迁移框架。

证据：`server/index.js`、`server/db/database.js::db.transaction/seedDatabase`、`server/routes/*.js`、`server/utils/http.js`、`server/middleware/{auth,error}.js`。

## 4. 关键业务模块依赖关系

| 关系 | 前端维护 | 后端维护 | 数据库维护 | 待专项核对的线索 |
| --- | --- | --- | --- | --- |
| 职位 ↔ 候选人 | 候选人表单硬编码职位名称；筛选按字符串匹配 | `candidates.js::adjustPositionCount` 按 title 增减人数；候选人更换职位时转移计数；`positions.js` 改名事务更新候选人/面试文本 | positions 有 ID，但 candidates 仅 position TEXT；title 不唯一，无职位外键 | 重名、删除、空格处理、改名、统计口径与可传人数值；仅记线索 |
| 候选人 ↔ 面试 | 安排时复制 candidateId/name/position；Store 拦截重复 scheduled；删除候选人后未同步清理已加载 interview Store | 面试创建/更新检查候选人存在与重复 scheduled；候选人编辑事务同步面试姓名和职位 | `interviews.candidate_id → candidates.id ON DELETE CASCADE`；姓名/职位冗余存储 | 外键级联与前端缓存一致性；提交冗余字段可信度；并发重复安排 |
| 面试状态 ↔ 招聘阶段 | 候选人列表先创建面试，再把 screening 推到 first_interview；面试列表先 completed，再依 stage/type 推进；详情另可手动推进/淘汰 | 两类资源各自更新；面试路由不自动更新候选人 stage；候选人路由无完整来源状态检查 | 两张表只有各自枚举 CHECK，无跨表阶段约束 | 单项操作部分成功、重新操作、并发及阶段与面试不一致 |
| Dashboard ↔ 业务数据 | 独立页面 ref，`Promise.all` 获取三份全量列表；本地日期和 computed 汇总；不读业务 Store | 复用三个 GET 列表，没有聚合或待办专用接口 | 读取基础表，不存汇总/历史快照 | 三份请求不保证同一数据快照；指标口径、缓存与日期更新策略待核对 |
| 登录状态 ↔ 受保护接口 | guards 检查 storage 与 expiresAt；Axios 加 Bearer，401 清理；浏览器本地检查不验证签名 | requireAuth 验签并设置 req.user；`/auth/me` 单独保护，其余业务统一挂载在 `/api` 认证之后 | 登录查 users；profile 按用户 ID；其他业务表未见用户/组织归属字段 | Token 生命周期、改密/退出后旧 Token、用户存在性及业务权限边界 |

关键联动链如下；两次请求之间没有共享事务：

```text
候选人列表.handleSubmitInterview
  → interviewStore.addInterview → POST /interviews → INSERT interviews
  → getStageAfterInterviewScheduled(stage)
  → 如 screening：PATCH /candidates/:id → UPDATE stage=first_interview

面试列表.handleComplete
  → PATCH /interviews/:id → UPDATE status=completed
  → candidateStore.fetchCandidateById（可命中已有缓存）
  → getInterviewCompletionNextStage(stage, type)
      初面 + first_interview → second_interview
      复面 + second_interview → offer
      其他组合（包括 HR 面）→ 不自动推进
  → 有下一阶段时 PATCH /candidates/:id

候选人详情.handleAdvanceStage / handleReject
  → 前端条件/确认框 → PATCH /candidates/:id → UPDATE candidates.stage
```

这些是当前实现事实，不代表已确认的招聘产品规则，也不在本批次决定替代方案。
